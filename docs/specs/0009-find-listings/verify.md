# Verify: find listings · spec 0009 · updated 2026-11-03

_Steps derived from spec 0009 acceptance criteria. `/check verify` runs these; `/test` locks the durable ones. Needs the backend running and seeded: the local database holds 40 public listings, so 4 pages of 12. A guest needs no account, and this feature only reads, so it leaves no data behind. The failure steps need the API to fail on purpose: stop the backend, or build the app (`npm run build`), start it on another port with `API_URL` pointing at a small stand in API that answers 500, 429 (with `Retry-After`), an empty list, a body that is not JSON, and no answer at all._

_Closed without a `/check verify` run on 2026-11-03 by the engineer's decision: the boxes below stay open on purpose, and the only evidence is the self checks of `/develop` listed here. Run them later if the feature misbehaves._

Self checked by `/develop` on 2026-11-03 against the real backend (Edge through `agent-browser`, dev server on 5173) for M1 to M4: `/` as a guest, a keyword search, the skeleton on every page and keyword change (the old results were gone about 70 ms after the address changed), the empty state, "Xóa tìm kiếm", back and forward, `/?page=99`, a script tag as the keyword, the odd addresses over `curl`, the card at 320, 390, 768 and 1280 px (columns, equal heights, no sideways scroll), the failed photo path by blocking `/_next/image`, the metadata of five addresses, `/robots.txt`, the `/dev/ui` section, the heading order, the focus ring on the search controls and page links, a clean console on four addresses in a fresh session, `npm run check` and `npm run build`. Against a production build with a stand in API: the 500, 429 (countdown and the disabled button), empty, not JSON, no answer (it gave up at 10.04 s) and refused connection states, the retry after the API came back, and that the API saw no `Authorization` and no cookie. Not run: a screen reader pass, a real 5xx from the backend, a signed in landlord looking at the page source, and a listing with no cover (the backend now needs 1 to 5 photos, so none exists; the placeholder shows only in `/dev/ui`).

Known gap found by the self check, for the engineer to decide: with scripts turned off the search form still submits, but the results (and the live search box) are streamed inside hidden containers that only scripts reveal, so a visitor without scripts sees the skeleton. Search engines are not affected (the content is in the HTML and Googlebot runs scripts). See the report of `/develop`.

Notes for a re-run: the keyword `zzzzzz` matches a real test listing titled "zzzzzzzz", so use `qqqqxjkw` for "nothing found". The form writes a space as `+` (`/?q=tan+dinh`), and `listingsHref` does the same, so both agree.
